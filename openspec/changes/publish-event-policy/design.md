## Context

See proposal.md for motivation and the measured ruleset. Sites re-resolved against 0.15.0 (`1b22eb6`): the hardcoded event `publish.py:147` (`_payload`), the policy model `policy.py:74-80` (`AutoPolicy` with `publish_state`), the base-ref reader `policy.py:117-131` (`resolve_auto_policy`), the summary contract `summary.py:248-259` (`ExecutionSummary`), the App argv `sandbox-auth.ts:125,151` (`publish?: "none" | "github-comment"`), the check facts `review-job.ts:152-165` (`diagnosticText`), the language gate line splitter `langgate.py:96-136`, the inline renderer `publication.py:79-107`, the 422 fallback `publish.py:268-281`, the check-run creation response handling `github-app.ts:282-292`.

A pre-implementation review by three independent readers (GitHub API semantics, fail-safety and abuse, repository contract) changed several decisions below; the two most consequential were that a GitHub App's GraphQL `author.login` is the bare slug while REST `user.login` carries the `[bot]` suffix, and that resolving threads before the replacement review is posted can strip a live finding of its gating thread.

## Goals / Non-Goals

Goals: make the review event a repository decision with today's behaviour as the default; give every inline finding a stable identity across heads; resolve rvw's own threads when the finding is gone and never duplicate a live one; keep every GitHub write attributable to rvw's own identity; never hide a non-rejected finding from the publication; record what happened in `summary.json` and the check facts. Non-goals: PASS/BLOCK evaluation, severities, adjudication, discovery, prompts, runtimes, deadlines, redispatch, lane content, `.rvw/config.yaml`, publication prose beyond the invisible markers, catalogs beyond the new keys, Terraform, workflows, `CHANGELOG.md`, the deployment repository, and any `auto.yaml` in a consuming repository.

## Decisions

1. **Policy shape.** `AutoPolicy` gains `publish: PublishPolicy` and `threads: ThreadPolicy`, both strict (`extra="forbid"`, strict scalars) with defaults `on_block: comment`, `on_pass: comment`, `dismiss_on_pass: false`, `approve_requires_explicit_opt_in: true`, `resolve_on_fix: true`, `reuse_open_thread: true`. The existing `publish_state: comment|none` keeps its meaning (whether `run`/`auto` publish at all); the new block decides *which* event. A validation error located under `publish` or `threads` is raised as `PublishPolicyInvalid` (reason `publish_policy_invalid`, detail `approve_not_opted_in` or the Pydantic location) so `run` exits 2 before review, like `presentation_config_invalid`; every other schema fault keeps `invalid_policy`.

2. **Policy provenance for publication.** `run`/`auto` resolve the policy at the base ref and persist it as `policy.json` (`{source, path, policy}`) through `RunHandle.save_policy`; `gate` resolves and persists it inside its checkout, `review` at the base ref of its target. Publication never resolves policy itself: the CLI helper `_publication_policy` hands `publish_review` an `AutoPolicy` and a `PublishPolicySource`. `rvw publish --run` re-reads the base ref when the repository is reachable from the current directory and otherwise uses the snapshot with every event above COMMENT clamped (`event_clamped_reason: snapshot_unverified`), because the run directory is writable by full-access lanes in the App. The deprecated external policy file is never consulted at publication time. `publish.policy_source` is `repository`, `explicit`, or `default`. A `PublishPolicyInvalid` at any publication site is a usage error (exit 2) reported as `publish_policy_invalid`; gate records it in `publish-status.json` first.

3. **Event selection** is a pure function `select_event(policy, verdict, *, clamp, has_prose)`. `verdict` is the policy PASS/BLOCK (`run`/`auto` evaluation, the gate verdict, or `evaluate` re-run by `publish --run`) or `None` for `review --publish`. BLOCK maps `on_block`; PASS maps `on_pass`, where `none` yields no review when `has_prose` is false and COMMENT otherwise. `has_prose` is true when the publication shows any non-rejected finding, an unreviewed region, or an unfinished rule set. A single `clamp` predicate forces COMMENT and disables dismissal and resolution: summary status `degraded` or `failed`, summary missing, language fallback in use, own identity unknown, any reconciliation read failed or truncated, or an unverified snapshot. APPROVE without prose sends `{"event": "APPROVE", "commit_id": ..., "body": "<review marker>"}`; with prose it carries the ordinary body and inline comments. Every payload pins `commit_id` to the reviewed head and every body ends with `<!-- rvw:v1 review head=<sha> event=<EVENT> -->`, so own reviews are recognisable by marker plus author and same-head matching is exact.

4. **Own identity.** An installation token cannot call `GET /user` or GraphQL `viewer`, so the Worker records `app.slug` from the check-run creation response (or `GET /repos/{o}/{r}/check-runs/{id}` when re-entering with an existing check) on the job record and passes `RVW_GITHUB_LOGIN=<slug>[bot]` through the process environment (`startProcess({env})`, which survives the script's `unset` line). Python parses that value, or `gh api user` for PAT users, into `OwnIdentity(login, kind)` with the `[bot]` suffix stripped: GraphQL authors match when `login` equals the bare slug and `__typename` is `Bot` for an App or `User` otherwise; REST users match when `login` equals the bare or suffixed form and `type` agrees. Nothing authored by another identity is ever read as rvw's, resolved, or dismissed. `publish.actor` records the REST form.

5. **Finding identity.** `threads.py` owns `normalize_evidence`, `fingerprint`, `build_marker`, `parse_marker`. Normalisation drops `path:line:`, `line:`, `line|`, and `L<n>` prefixes from quoted lines, collapses whitespace runs, strips trailing punctuation, and drops empty lines; line numbers never enter the digest. The inline marker is one HTML comment appended after a blank line: `<!-- rvw:v1 fp=<16 hex> rule=<rule_id> lane=<lane_id> -->`, `lane` being the group's first lane id. `parse_marker` takes the last marker in a thread's first comment, so a marker quoted in evidence or injected into prose cannot override the one rvw appended. The language gate protects only the exact rvw marker pattern, not arbitrary HTML comments, so injected comments are still scored as prose; the rewrite validator rejects replacements that contain one. Markers are stripped from the 422 fallback body. `report.md` is unchanged.

6. **Thread reading.** GraphQL `pullRequest.reviewThreads` is paginated by cursor (100 per page, bounded) with `id`, `isResolved`, `isOutdated`, `subjectType`, `path`, `line`, `originalLine`, and the first fifty comments' `body`, `author { login __typename }`, and `originalCommit { oid }`. A thread is rvw's when its first comment carries a marker and its author matches the identity. A thread with any comment by another identity, or more comments than the page, is human-engaged. Read failures, malformed pages, or truncation mark the reconciliation as failed (`threads_skipped_reason: read_failed`) and trigger the clamp; they never abort publication. Dry-run performs these reads only for `rvw publish --run` (planning); `review` and `gate` dry-runs neither read nor write.

7. **Reconciliation** (`reconcile_threads`) takes the candidates (every non-rejected group with a path, flagged `inline` when it would be posted as a comment), rvw's threads, the identity, H2, the lane validity map, H2 changed paths, budget-excluded paths, H2 hunks and per-lane uncovered hunk ids, and a diff provider. Step 1 matches fingerprints, valid only when the fingerprint is unique among rvw's threads and among candidates on that path. Step 2 groups the rest by `(rule_id, path)`: a non-outdated thread's position is GitHub's `line`; an outdated thread's `originalLine` is mapped through the hunks of `<originalCommit>..<H2>` for the path (local `git diff` when both objects exist, else `compare/<originalCommit>...<H2>` accepted only when `merge_base_commit.sha == originalCommit`, with `--- a/` and `+++ b/` headers synthesised in front of the header-less `patch`); a mapped line carrying a same-rule candidate is a match; exactly one remaining thread and one remaining candidate is a match regardless of mapping; two threads claiming one candidate, or two or more unmappable threads beside remaining candidates, are ambiguous. Outcomes: `reused` (matched open thread; the candidate is not posted inline again and stays in the body), `superseded` (matched, outdated, inline candidate: post it again, then reply and resolve the old thread), `skipped_resolved` (matched or would-be-resolved thread already resolved; a matched one suppresses the inline repost), `ambiguous` (left open; no same-pair candidate posted inline), and for unmatched open threads in order: `skipped_degraded`, `skipped_same_head` (`originalCommit == H2`), `skipped_human_reply`, `skipped_lane_invalid` (lane invalid or absent on H2), `skipped_unverified` (no evidence of change: mapping unavailable, or the original line outside every hunk of the head-to-head diff while the path is still in the PR), `skipped_uncovered` (path budget-excluded or the mapped line's H2 hunk in the lane's uncovered list), `skipped_policy` (`resolve_on_fix: false`), else `resolved`. `reuse_open_thread: false` leaves matched threads untouched and posts every candidate.

8. **Order of GitHub operations** for head H2: render and language-gate every document including the catalog reply and dismissal texts; read the PR head, own reviews (REST, 100 per page), and threads; compute the plan; if the live head differs from H2 skip every write (`publication_skipped: head_moved`); if an own marked review for H2 already exists with the selected event and nothing new would be posted inline, skip the review (`publication_skipped: duplicate_review_same_head`, always for a second REQUEST_CHANGES); otherwise POST the review with the policy event and only unmatched inline candidates, retrying body-only once on 422 only when the payload carried comments and never changing the event. Only after a successful POST (or a legitimate no-POST) resolve `resolved` threads with `resolveReviewThread(resolutionReason: ADDRESSED)`, counting a thread only when the response says `isResolved`; supersede only candidates that were actually posted inline (the 422 fallback leaves outdated threads open). On PASS with `dismiss_on_pass` and no clamp, `PUT /pulls/{n}/reviews/{id}/dismissals --method PUT` with the catalog message for own marked reviews in state `CHANGES_REQUESTED` whose `commit_id` is not H2; on a non-2xx the review is re-read and recorded as dismissed only when its state is `DISMISSED`, otherwise under `dismiss_failed_review_ids`. GraphQL errors are surfaced from the response body (`errors[].type`): `FORBIDDEN` stops further writes (`threads_skipped_reason: forbidden`), `NOT_FOUND` counts the thread as missing.

9. **Recorded facts.** `ExecutionSummary.publish` (`PublishFacts`: `event`, `policy_source`, `actor`, `event_clamped_reason`, `dismissed_review_ids: list[int]`, `dismiss_failed_review_ids`, `resolved_thread_ids`, `reused_thread_ids`, `superseded_thread_ids`, `threads_ambiguous`, `threads_skipped_lane_invalid`, `threads_skipped_resolved`, `threads_skipped_same_head`, `threads_skipped_human_reply`, `threads_skipped_unverified`, `threads_skipped_uncovered`, `threads_skipped_missing`, `threads_skipped_reason`) and top-level `publication_skipped` beside `publication_failure`; `publish_review` persists them itself after the last GitHub operation. `PublishResult` gains `event` and `skipped` and widens `state`. `ProcessResult` is unchanged except the `runtime.publish` enum. The Worker parser accepts the new summary fields as optional in the same commit Python starts emitting them, and `diagnosticText` carries them verbatim; the summary sentence is untouched.

10. **Publish mode rename.** `--publish github-review` is canonical; `github-comment` is accepted for one release with a stderr deprecation warning and normalised before recording. `RuntimeSettings.publish`, `process.schema.json`, and the Worker parser accept `none`, `github-review`, and `github-comment`. `--allow-approve` stays non-enabling and says so. Because a Cloudflare container rollout is asynchronous, a sandbox can briefly run the previous image while the Worker already emits `github-review`; that window ends as a neutral check and is documented.

## Risks / Trade-offs

- A bot APPROVE never satisfies code-owner review and may count toward `required_approving_review_count`; GitHub defines `require_last_push_approval` as approval by someone other than the pusher, which a bot approval may also satisfy → documented; the consuming repository owns that risk and must opt in twice.
- Resolving a thread wrongly grants a free pass under `required_review_thread_resolution` → resolution requires own identity, a marker, a valid lane, a changed region, coverage of that region, no same-head origin, no human reply, no clamp, and a successful review write; anything uncertain stays open. A thread fixed indirectly (by a change elsewhere) stays open for manual resolution, which is today's behaviour.
- Fingerprints over adjudication evidence will often differ between heads because the evidence is model-written → the fingerprint is the fast path; the line-mapping and unique-pair steps carry the common case.
- Dry-run planning reads GitHub for `rvw publish --run` → reads are tolerated failures; writes remain execute-only; the earlier "no network call" wording is narrowed to "no GitHub write".
- The compare API returns at most 300 files and only merge-base diffs → a missing patch or a non-ancestor original commit is an unavailable mapping, which can only leave threads open, never resolve them.

## Migration Plan

Four conventional commits on one branch: policy blocks; fingerprint, markers, thread reconciliation, recorded thread facts (with Worker parser acceptance); policy-selected event with identity, idempotency, and dismissal; App rename, slug plumbing, and check facts. Legacy `summary.json` without the new fields loads with defaults in both Python and the Worker. Threads published before this change carry no marker and are never touched. No push, deployment, or archive.

## Post-implementation verification (2026-09-08)

An adversarial review of the four commits (28 agents, 18 confirmed findings) led to a fifth commit: thread and dismissal writes after the review POST never raise (`write_failed` recorded, facts always persisted); an unverified snapshot and a missing adjudication outcome clamp reconciliation as well as the event; the clamp reason is recorded whenever a clamp applies; a matched outdated thread whose supersession is withheld is reused rather than re-posted; fingerprint uniqueness ignores resolved predecessors; the compare API never reports an absent path as unchanged; renamed paths have not left the diff; local `git diff` disables drivers and prefixes; the deprecated external policy never decides the event; gate resolves its policy before dispatch and publishes with it; publication sites label non-publish faults `invalid_policy`; a `review` dry run tolerates a malformed base policy with a warning.
